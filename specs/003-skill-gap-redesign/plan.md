# pm-journey スキルギャップ改善計画

## この文書について

pm-journeyの現行シナリオで「PMアシスタントとしてプロジェクトに参加できるレベル」に到達するために、何が足りていて、何が足りていないかを整理し、改善策を提案する。

---

## 1. 現状の評価

### 現行シナリオでカバーできていること

| スキル | 該当シナリオ | 習得レベル |
|--------|-------------|-----------|
| 自己紹介・チームへの合流 | basic-intro-alignment | 基礎 — 書くだけ、フィードバックループなし |
| プロダクト理解のヒアリング | basic-product-understanding | 良好 — 対話型で掘り下げる体験がある |
| 議事録作成 | basic-meeting-minutes | 基礎 — 単発提出、改善サイクルなし |
| テストケース設計 | test-login / form / file-upload | 良好 — 反復的にエージェントとやり取りしながら網羅性を高める |
| 要件定義書の作成 | requirement-definition 3種 | 良好 — モックアップ付きで具体的 |
| 障害対応 | incident-response 3種 | 良好 — P1〜P3で緊急度を変えた体験ができる |
| 事業戦略判断 | business-execution 3種 | 良好 — データ提示あり、トレードオフを言語化させる |

### 決定的に不足しているスキル領域

以下は現実のPM業務で毎日使うが、pm-journeyで一切触れていない領域。

#### A. ステークホルダー間の利害衝突のハンドリング

現状: すべてのシナリオが「ユーザー vs AIエージェント（1対1）」。AIは協力的なメンターとして振る舞う。

現実: PMの仕事の大部分は「エンジニアは"技術的負債を返したい"、営業は"今月中にこの機能が必要"、デザイナーは"UXを妥協したくない"」という板挟みの中で合意を形成すること。誰も間違っていないのに全員の要望は通せない状況で、どう優先順位を付け、どう納得してもらうかが問われる。

#### B. バックログの優先順位付け（フレームワーク適用）

現状: レクチャーでRICE/ICEに言及しているが、実際にフレームワークを使って10個のバックログアイテムを並べ替える体験はゼロ。

現実: スプリントプランニングのたびに「どれを先にやるか」を決める必要があり、感覚ではなく再現可能な基準で判断できることがPMアシスタントに求められる最初のスキル。

#### C. データ・メトリクスの読み取りと意思決定

現状: adv-data-roiシナリオでデータは提示されるが、ダッシュボードUIやグラフはなく、テキストベースで数値が列挙されるだけ。視覚的なデータ解釈の練習にはなっていない。

現実: PMは毎日Mixpanel/Amplitude/Lookerのようなダッシュボードを見て「この数字は何を意味するか」「どの指標が異常か」を判断する。

#### D. PRD（プロダクト要件ドキュメント）の作成

現状: 要件定義シナリオは「ログイン」「フォーム」「ファイルアップロード」の個別機能仕様に特化。PRDの構造（背景、目的、成功指標、スコープ内外、ユーザーストーリー、リリース基準）を一通り書く体験がない。

現実: PMアシスタントが最初に任される仕事として「このフィーチャーのPRDを書いて」は非常に多い。

#### E. フィードバックを受けて改善するサイクル

現状: 全シナリオが「1回提出 → 評価」で完結。提出後のフィードバックを反映して2稿目を出す経験がない。

現実: PRDもテストケースも議事録も、最初のドラフトがそのまま通ることはほぼない。レビューコメントを受けて改善するプロセスそのものがスキル。

#### F. スプリントプランニング / デイリーのファシリテーション

現状: レクチャーで「月曜: スプリントプランニング」と触れるが、実際に「このスプリントに何を入れるか」を決めるシナリオがない。

現実: PMアシスタントは早い段階でプランニングミーティングの進行やアジェンダ作成を任される。

---

## 2. 改善提案

優先度順に並べる。各提案は「既存システムの技術的制約内で実現可能」かどうかも評価する。

### Phase 1: 既存の仕組みを活かして追加できるシナリオ（工数: 小〜中）

これらは現行のシナリオタイプ・インタラクションパターン・エージェントプロンプト構造をそのまま使える。

#### 1-1. バックログ優先順位付けシナリオ（新規）

**概要**: 10個のバックログアイテム（機能要望・バグ修正・技術的負債）が与えられ、RICE/ICEフレームワークを使って優先順位を付ける。

**インタラクション**: BusinessExecutionレイアウト（フォーム4セクション + チャット）をそのまま使用
- セクション1: 各アイテムのReach/Impact/Confidence/Effortを記入
- セクション2: 優先順位の並び順と根拠
- セクション3: 「やらない」と決めたアイテムの理由
- セクション4: 上位3件の実行計画

**エージェントの役割**: ユーザーが見落としている観点（技術的負債の放置コスト、営業が約束した納期など）を質問として投げかける。正解を教えるのではなく、判断の抜け穴を突く。

**評価基準**: フレームワークの正しい適用 / 根拠の明確さ / トレードオフの認識 / ステークホルダーへの説明力

**技術的実現性**: ★★★ 既存のBusinessExecutionパターンそのまま。バックエンドにシナリオ定義を追加するだけ。

---

#### 1-2. PRD作成シナリオ（新規）

**概要**: 「新機能: ユーザー通知設定画面」のPRDをゼロから書く。背景・目的・成功指標・スコープ内外・ユーザーストーリー・リリース基準のテンプレートが提供される。

**インタラクション**: RequirementDefinitionレイアウトを使用
- 左側: PRDテンプレート（セクションごとの入力フォーム）
- 右側: チャットでエージェントに質問できる

**エージェントの役割**:
- 「成功指標が曖昧です。"通知設定の利用率"は何%を目指しますか？」のように具体性を要求
- 「スコープ外に"プッシュ通知"は含まれますか？明記してください」のように漏れを指摘
- PRDの各セクションについて、実際のレビューアー（エンジニアリードやデザイナー）が聞きそうな質問をぶつける

**評価基準**: 背景の明確さ / 成功指標の具体性・測定可能性 / スコープの明確な線引き / ユーザーストーリーの網羅性

**技術的実現性**: ★★★ RequirementDefinitionレイアウトにフォームセクションを追加する程度。新しいUIコンポーネントは不要。

---

#### 1-3. ステークホルダー利害衝突シナリオ（新規）

**概要**: 「リリース1週間前。エンジニアリードが"このままだとバグが残る、延期すべき"、営業部長が"顧客に来月リリースと約束した、延期は許されない"、デザイナーが"UIの一部が未完成、このまま出すとブランド毀損"と主張。あなたはPMとしてどう対応するか。」

**インタラクション**: チャットベース（SoftSkillsパターン）。ただしエージェントは**協力的メンターではなく、3人のステークホルダーを演じ分ける**。
- ユーザーが「エンジニアリードに質問したい」と言えばエンジニアとして返答
- ユーザーが「営業部長を説得したい」と言えば営業として反論
- ユーザーが最終決定を提示すれば、各ステークホルダーの反応を返す

**ミッション**:
1. 各ステークホルダーの懸念を正確に把握する
2. 選択肢を洗い出す（全リリース / 一部機能カット / 延期 / etc.）
3. 最終判断とその根拠を全員に伝える
4. フォローアップアクションを決める

**評価基準**: 情報収集の網羅性 / 各立場への共感と理解 / 判断の論理性 / コミュニケーションの適切さ

**技術的実現性**: ★★☆ シナリオ定義とエージェントプロンプトの追加で対応可能。ただしエージェントに「複数人格の演じ分け」を求めるため、プロンプトエンジニアリングの難易度が高い。十分なテストが必要。

---

#### 1-4. 議事録シナリオの改善（既存改修）

**現状の問題**: 会議ログを読んで議事録を1回提出するだけ。フィードバックループがない。

**改善案**: 提出後にエージェントが「決定事項のうち"デザインレビューの日程"が抜けています」「Next Actionのオーナーが明記されていません」といった具体的レビューコメントを返し、**2回目の提出**を求める。2回目の提出で最終評価を行う。

**技術的実現性**: ★★☆ `single_response: true`を外してチャットベースに変更する必要がある。セッションのメッセージフローを少し変える。エージェントプロンプトで「1回目はレビュー、2回目で評価」という2段階の振る舞いを指示する。

---

### Phase 2: 小規模なUI拡張が必要なシナリオ（工数: 中）

#### 2-1. メトリクスダッシュボード読み取りシナリオ（新規）

**概要**: モックのダッシュボードUI（棒グラフ、折れ線グラフ、ファネル図）を見て、「何が起きているか」「どのアクションを取るべきか」を判断する。

**新規UIコンポーネント**: `DashboardMockup` — SVGベースの簡易チャートコンポーネント
- DAU/MAU推移の折れ線グラフ
- ファネル（登録→オンボーディング→課金→継続）の棒グラフ
- コホート別リテンション率のヒートマップ

**インタラクション**: BusinessExecutionレイアウト
- 左側: DashboardMockup（インタラクティブではないが視覚的に情報量がある）
- 右側: フォーム + チャット
- セクション1: データから読み取れる事実（What）
- セクション2: 原因の仮説（Why）
- セクション3: 推奨アクションと期待される効果（So what）

**評価基準**: データ読解の正確性 / 仮説の論理性 / アクションの具体性と優先順位

**技術的実現性**: ★★☆ SVGチャートコンポーネントの新規作成が必要（LecturePage.tsxのダイアグラムと同じアプローチでOK）。レイアウト自体は既存パターンを流用。

---

#### 2-2. スプリントプランニングシナリオ（新規）

**概要**: 2週間スプリントのバックログ（15アイテム、合計ポイント > キャパシティ）から「今回のスプリントに入れるもの」を選ぶ。チームのベロシティは40ポイント。

**新規UIコンポーネント**: `BacklogBoard` — ドラッグ可能なカードリスト
- 左: バックログ（全アイテム、ポイント付き）
- 右: スプリントスコープ（選択済みアイテム、合計ポイント表示）
- ドラッグ&ドロップでアイテムを移動

**インタラクション**:
- ボードでアイテムを選択/除外
- チャットでエージェントに質問（「このアイテムの依存関係は？」「QAの工数は含まれている？」）
- エージェントは追加情報を出す（「このアイテムはデザインレビューがまだ終わっていません」「営業がデモで使いたいと言っています」）
- 最終的なスプリントスコープを提出

**評価基準**: キャパシティの適切な管理 / 依存関係の考慮 / ビジネス優先度とのバランス / リスクへの対処

**技術的実現性**: ★☆☆ ドラッグ&ドロップUIは新規開発が必要。ただしシンプルなカードリストで十分であり、ライブラリ（dnd-kit等）を使えば妥当な工数。

---

### Phase 3: 構造的な変更が必要な改善（工数: 大）

#### 3-1. フィードバック→改善サイクルの仕組み化

**現状の問題**: すべてのシナリオが「1回提出 → 最終評価」。

**改善案**: 新しいセッションフロー「ドラフト→レビュー→改善→最終評価」を導入。

```
ユーザーがドラフト提出
  ↓
エージェントが構造化レビューを返す（良い点 / 改善点 / 具体的な質問）
  ↓
ユーザーが改善版を提出
  ↓
最終評価（2回目の提出内容 + 改善プロセス自体も評価対象）
```

**対象シナリオ**: 議事録、PRD、要件定義、テストケース全般

**技術的変更点**:
- セッション状態に `draft_count` / `revision_phase` を追加
- エージェントプロンプトに「1回目はレビューモード、2回目は評価モード」の切り替えロジック
- 評価基準に「改善の質」（1回目→2回目でどれだけ改善したか）を追加
- UIに「ドラフト提出」と「最終提出」の2段階ボタン

**技術的実現性**: ★☆☆ セッションモデルの拡張、エージェントプロンプトの大幅変更、UI変更が必要。ただし根本的なアーキテクチャ変更ではなく、既存の仕組みの拡張で対応可能。

---

#### 3-2. マルチステークホルダーシミュレーション基盤

**1-3の発展版**: エージェントが単一ペルソナではなく、シナリオ内で複数のNPC（ステークホルダー）を管理する基盤。

**技術的変更点**:
- シナリオ定義に `stakeholders: Vec<Stakeholder>` を追加（名前、役割、性格、優先事項、譲れない点）
- エージェントプロンプトにステークホルダーリストを注入
- UIでステークホルダーごとのアバターやラベルを表示（「🧑‍💻 田中 (Eng Lead)」「💼 佐藤 (Sales Director)」）
- メッセージにステークホルダーIDをタグ付け

**対象シナリオ**: 利害衝突、スプリントプランニング、Go/No-Go判断

**技術的実現性**: ★☆☆ バックエンドのモデル拡張 + フロントのチャットUI拡張 + プロンプトエンジニアリング。最も工数が大きいが、PMスキル習得のインパクトも最大。

## 4. カテゴリ構成の見直し

新シナリオ追加に伴い、ロードマップのカテゴリ構成も見直す。

### 現行（5カテゴリ）

1. 基礎ソフトスキル（3シナリオ）
2. テストケース作成（3シナリオ）
3. 要件定義（3シナリオ）
4. 障害対応（3シナリオ）
5. 事業推進・戦略（3シナリオ）

### 提案（7カテゴリ）

1. **基礎ソフトスキル**（3 → 4シナリオ）— 既存3 + ステークホルダー利害衝突
2. **プランニングと優先順位**（新規カテゴリ、2〜3シナリオ）— バックログ優先順位付け + スプリントプランニング
3. **PRDと仕様策定**（新規カテゴリ、1〜2シナリオ）— PRD作成（+ 将来的にAPI仕様、画面仕様など）
4. **テストケース作成**（3シナリオ）— 変更なし
5. **要件定義**（3シナリオ）— 変更なし
6. **障害対応**（3シナリオ）— 変更なし
7. **事業推進・戦略**（3 → 4シナリオ）— 既存3 + メトリクスダッシュボード読み取り

**注意**: カテゴリを増やすとロードマップのマイルストーン・進捗計算・修了証のロジックすべてに影響する。段階的に追加し、既存ユーザーの進捗データを壊さないよう注意が必要。

## 5. レクチャー（Step 0）との整合性

新シナリオを追加する場合、Step 0のレクチャー内容も更新が必要。

| レクチャー | 更新内容 |
|-----------|---------|
| Lecture 2: コアスキル | 「優先順位付け」セクションに「バックログ優先順位付けシナリオで実際にRICEを使う体験ができます」を追加 |
| Lecture 3: 日常業務 | 「スプリントプランニング」セクションにシナリオへのリンクを追加 |
| Lecture 4: スキルマップ | 新カテゴリ（プランニング、PRD）を追加し、Step数を更新 |

## 6. まとめ

pm-journeyは「PMの業務を断片的に体験する」段階としては良くできているが、「プロジェクトに参加できるレベル」に到達するには以下の3つが不足している:

1. **人との衝突を乗り越える体験**（ステークホルダー対立シナリオ）
2. **フレームワークを実際に使う体験**（RICE/ICEでバックログを並べる、PRDテンプレートを埋める）
3. **フィードバックを受けて改善する体験**（ドラフト→レビュー→改善サイクル）

Phase 1の3シナリオ（バックログ優先順位付け、PRD作成、議事録改修）を追加するだけで、「コースを修了した人がPMアシスタントとして最低限動ける」という状態にかなり近づく。
